# Security Policy

## Security Overview

This project implements security best practices based on the **OWASP Top 10 Security Risks**.
Specifically for **OWASP A06: Vulnerable and Outdated Components**, we maintain continuous vulnerability management across all application dependencies, container images, and deployment configurations.

---

## OWASP A06: Vulnerable and Outdated Components Compliance

### 1. Dependency Management Strategy

- **Exact Version Pinning**: All production dependencies in `requirements.txt` are pinned with exact versions to ensure reproducible and deterministic builds.
- **Continuous Vulnerability Auditing**: Dependencies are scanned against known Common Vulnerabilities and Exposures (CVE) databases using `pip-audit`.
- **Patched Packages**: Known vulnerable packages (such as legacy `python-multipart` or outdated `fastapi` versions) are patched immediately upon release of fix versions.

### 2. Automated Dependency Security Scanning

- **Pre-commit & Local Audit**: Developers can run the dependency audit locally at any time:
    ```bash
    python scripts/audit_dependencies.py
    ```
    Or directly using `pip-audit`:
    ```bash
    pip-audit -r requirements.txt
    ```
- **CI/CD Security Workflow**: GitHub Actions automatically runs `scripts/audit_dependencies.py` on every `push`, `pull_request`, and daily via scheduled cron job (`.github/workflows/security-audit.yml`).

### 3. Automated Dependency Updates (Dependabot)

- Dependabot is configured via `.github/dependabot.yml` to check daily for Python package security updates and weekly for Docker container image updates.
- Security pull requests generated by Dependabot are prioritized and reviewed promptly.

## OWASP A07: Identification and Authentication Failures Compliance

### 1. Anti-Brute-Force & Account Lockout

- **Account Lockout**: After 5 (`MAX_FAILED_LOGIN_ATTEMPTS`) consecutive failed password attempts, the account is temporarily locked for 15 (`ACCOUNT_LOCKOUT_MINUTES`) minutes.
- **Per-IP Rate Limiting**: All authentication endpoints (`/login`, `/register`, `/forgot-password`, `/verify-otp`, `/reset-password`, `/change-password`) are strictly rate-limited per IP using `slowapi`.

### 2. User Enumeration & Timing Attack Countermeasures

- **Generic Responses**: Authentication failure messages return generic feedback ("Invalid login credentials") without revealing if the username or email exists.
- **Constant-Time Verification**: A pre-computed dummy BCrypt hash verification (`verify_dummy_password()`) is performed when an invalid user ID is provided to ensure consistent response timing.

### 3. Password Security & Breached Password Blocklist

- **BCrypt Hashing**: Passwords are hashed using BCrypt (`cost=12`).
- **Complexity Enforcer**: Passwords must contain at least 8 characters, upper & lowercase letters, digits, and special characters.
- **Common Breached Password Blocklist**: Rejects passwords found in top breached password lists (e.g. `password123`, `admin123!`).
- **Contextual Restrictions**: Passwords cannot contain the user's username or email local-part.

### 4. Session Security & Session Invalidation

- **Server-Side Sessions**: Authentication uses database-backed sessions (`user_sessions` table). The raw session token lives exclusively in an `HttpOnly`, `SameSite=Strict`, `Secure` cookie (`session_id`); only its SHA-256 hash is stored at rest.
- **Configurable Lifetime**: Sessions last 7 days by default or 30 days when the user opts in via `remember_me: true`.
- **Immediate Revocation on Logout**: Calling `POST /api/auth/logout` marks the session `revoked = true` in the database, invalidating any future use of the cookie even before its natural expiry.
- **Session Revocation on Password Change/Reset**: Password resets and authenticated password changes (`POST /api/auth/change-password`) automatically revoke all active sessions across all devices.
- **Immediate Revocation on Admin Status Change**: When an admin sets a user's status to `suspended`, `banned`, or `inactive`, all active sessions for that user are immediately revoked, forcing an instant logout across all devices.

## OWASP A08: Software and Data Integrity Failures Compliance

### 1. Cryptographic Data Signatures & Payload Integrity

- **HMAC-SHA256 Payload Signatures**: Critical data tokens and state payloads are signed with HMAC-SHA256 using `app/core/integrity.py` (`generate_data_signature`, `sign_payload`).
- **Constant-Time Verification**: All signature checks use `hmac.compare_digest` to prevent timing side-channel attacks during payload verification.

### 2. Cryptographic Payload Integrity

- **HMAC-SHA256 Payload Signatures**: Critical data tokens and state payloads are signed with HMAC-SHA256 using `app/core/integrity.py` (`generate_data_signature`, `sign_payload`).
- **Constant-Time Verification**: All signature checks use `hmac.compare_digest` to prevent timing side-channel attacks during payload verification.

### 3. Safe Deserialization & Structural Validation

- **Pydantic Strict Type Enforcement**: Input data is parsed exclusively using Pydantic schemas to prevent mass-assignment and structural data corruption.
- **No Unsafe Deserializers**: The application avoids unsafe Python deserialization tools (`pickle`, `marshal`, `eval`, or un-validated YAML loading).

## OWASP A09: Security Logging and Monitoring Failures Compliance

### 1. Centralized Structured Logging & SIEM Integration

- **Structured JSON Logging**: Production environments use `JSONFormatter` in `app/core/logging.py` to format all application logs as structured JSON objects containing standard metadata (`timestamp`, `level`, `logger`, `message`, `request_id`, `client_ip`, `user_agent`).
- **Configurable Storage & Formatting**: Controlled via `LOG_LEVEL`, `LOG_FORMAT` (`json` / `text`), and `LOG_FILE_PATH` settings. Rotating log files ensure logs are persisted with size management.

### 2. Request Correlation & Distributed Tracing

- **Correlation ID (`X-Request-ID`)**: `CorrelationIdMiddleware` (`app/core/middleware/correlation.py`) assigns a unique UUID4 to every incoming HTTP request (or adopts client `X-Request-ID`) and returns it in HTTP response headers.
- **Context-Bound Scope**: `ContextVar` propagation binds `request_id`, `client_ip`, and `user_agent` across all asynchronous execution contexts so every log record emitted during a request lifecycle includes correlation context.

### 3. Automatic Sensitive Data Redaction & Sanitization

- **Credential & Secret Protection**: `SensitiveDataRedactor` log filter automatically redacts sensitive attributes (`password`, `current_password`, `new_password`, `token`, `access_token`, `refresh_token`, `otp`, `secret_key`, `authorization`, `cookie`) across dictionaries, lists, and log message strings (`***REDACTED***`).
- **Log Injection Defense**: `sanitize_for_log` strips newline control characters (`\n`, `\r`) from untrusted strings to prevent log forging attacks.

### 4. Security Event Audit Logging System

- **Standardized Security Audit Events**: `AuditLogger` (`app/core/audit.py`) records all high-priority security audit events with defined event types (`AuditEventType`) and status codes (`SUCCESS`, `FAILURE`, `BLOCKED`, `ALERT`).
- **Audited Security Events**:
    - Authentication: `AUTH_REGISTER_SUCCESS`, `AUTH_LOGIN_SUCCESS`, `AUTH_LOGIN_FAILED`, `AUTH_LOCKOUT_TRIGGERED`, `AUTH_LOGOUT`.
    - Password Management: `PASSWORD_RESET_REQUESTED`, `PASSWORD_RESET_SUCCESS`, `PASSWORD_CHANGE_SUCCESS`, `PASSWORD_CHANGE_FAILED`.
    - Access Control & Authorization: `ACCESS_DENIED_UNAUTHENTICATED`, `ACCESS_DENIED_UNAUTHORIZED`, `ACCOUNT_STATUS_DENIED`.
    - Threat Defenses: `HONEYPOT_TRIGGERED`, `RATE_LIMIT_EXCEEDED`, `INTEGRITY_CHECK_FAILED`.
    - Administration: `ADMIN_USER_LISTED`, `ADMIN_USER_VIEWED`, `ADMIN_USER_STATUS_CHANGED`.

## Reporting a Vulnerability

We take the security of our application seriously. If you discover a security vulnerability or a vulnerable component, please follow these steps:

1. **Do NOT open a public GitHub issue.**
2. Send a detailed report to `security@yourdomain.com` (or create a private GitHub Security Advisory).
3. Include the following details:
    - Type of issue (e.g., vulnerable dependency, CVE ID, misconfiguration).
    - Affected component name and version.
    - Proof of Concept (PoC) or steps to reproduce.
    - Potential impact of the vulnerability.

### Response SLA

- **Initial Acknowledgment**: Within 24 hours.
- **Triage & Severity Assessment**: Within 48 hours.
- **Remediation & Patch Release**: Critical vulnerabilities patched within 7 days.
